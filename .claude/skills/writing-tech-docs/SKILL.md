# 写深入浅出的技术文档

## 核心原则

读者要的不是"覆盖全部知识点的手册"，而是**一场被设计过的理解之旅**：先钩住，再分层爬升，中途亲手验证，最后看清本质。

文章由以下六个部分按序构成（顺序即结构，缺一即败笔）：

## 第 0 步：动笔前，先定位系列坐标

个人博客多为连载系列，写作前后都要和旧文发生关系（这是结构的一部分，不是可选装饰）：

1. **查系列上下文**：到文章目录搜同领域旧文，重点读最近一篇的收尾"下一站"——那里埋着待兑现的伏笔。front matter 规范（文件名、`last_modified_at` 取最后一次 git 提交时间等）以仓库 CLAUDE.md 为准，不要凭空编日期。
2. **开头兑现伏笔**：续篇第一段承接上一篇埋的钩子。**引用旧文必须打开旧文核对原文**——逐字引用或忠实转述，禁止凭记忆写"上一篇说过 X"；引用与原文对不上是连载最严重的事故。跨篇链接用 permalink 格式 `/yyyy/mm/dd/标题.html`。
3. **中途回指**：复用旧文概念时一句话+链接带过（"上一篇讲过的阻塞语义，这里队列替你用了"），不整段重讲。
4. **收尾埋新伏笔**："下一站"必须埋一个**具体悬念**——一个现象、一句反直觉的话，让下一篇有明确的兑现点；"还有 X 值得探索"这类空话不算埋伏笔。

标题采用双段式：`技术名：一个反直觉断言或比喻`（如"git 从不记录你改了什么：diff 格式深读"）。

## 文章骨架（正面模板）

### 1. 钩子（开头 3 段以内必须出现其一）

- 一个读者真实踩过的坑 / 熟悉的困惑（"改了 CSS 用户却看不到新版"）
- 一个反直觉的事实或提问（"调用生成器函数时，函数体一行都没执行"）
- 一段可运行的 5 行代码，其输出违背读者预期

❌ 不要以"X 是一种……的技术"这类定义句开头。

### 2. 分层爬升（每层回答读者当下的一个问题）

| 层 | 读者状态 | 本层回答的问题 |
|---|---|---|
| L1 会用 | "先让我跑起来" | 最小可用做法是什么？ |
| L2 懂原理 | "它为什么这样工作？" | 底下发生了什么？ |
| L3 想得透 | "为什么非得这样设计？" | 换个设计行不行？代价是什么？ |

- 每层开头用一句话点明"你现在在哪一层"（如"到这里你已经会用了，但……"）。
- 相邻层之间必须有**台阶句**制造求知缺口："但这解释不了下面这个现象……"

### 3. 本质段落（全文的灵魂，L3 层的核心）

用一句话或一个心智模型回答："去掉所有术语后，这东西**到底是什么**？"

- 好的本质："生成器 = 把函数的执行状态变成可以拿在手里、随时暂停恢复的东西"
- 好的本质："HTTP 缓存 = 在'不问了省流量'和'问一句保新鲜'之间的信任分级"
- 检验标准：读者能用这句话向同事解释该技术，而不引用任何术语。

再追问一层设计权衡：**为什么是这个方案而不是显然的替代方案？**（列表 vs 生成器、绝对时间 vs 相对时间）说清被否决方案的失败场景，本质才立得住。

### 4. 趣味元素（散布全文，每千字至少一处）

- **生活化类比**：贴近读者真实经验的（外卖/快递/图书馆借阅），避免陈词滥调（造车、盖楼慎用）
- **历史/八卦**：这个设计当年是为了解决什么纠纷或事故？（PEP 背后的故事、某个 bug 的代价）
- **反直觉时刻**：主动指出"你以为 X，其实 Y"
- 幽默克制：一两处轻巧的比喻即可，不抖机灵、不用网络梗堆砌

### 5. 动手环节（实践性 = 读者亲手做，不是看代码）

- 至少一个**可复制运行的最小实验**（≤10 行），并给出**预期输出**——预期输出必须是**真实运行的摘录**；写作时环境跑不了的实验，明确标注"以下为示意输出"，禁止编造终端输出冒充实测。
- 至少一处"先预测再看答案"：让读者猜输出/猜行为，再揭示
- 收尾留 1-2 个**自测问题**（能答出说明真懂了，答案指向文中某节）

❌ 只贴示例代码让读者"参考"不算实践。

### 6. 收尾地图（不是知识点复述）

- 一张速查表 / 决策表（什么场景用什么方案）
- 指向下一站：学会这个后，再看什么会"原来如此"

## 证据纪律（全篇适用，L3 历史与设计动机是重灾区）

全文的关键断言只有三种合法形态，各就各位：

- **实测**：给出复现命令 + 输出摘录。
- **有据**：给出处——RFC/文档/源码的**可点链接**（"RFC 793"四个字不算出处）。引用外部原文与引用仓库旧文同规则：没核对过原文就改成间接转述，不逐字引用。
- **存疑**：凭记忆的日期、数字、他人系统默认值，明确降级——"印象中……未核实，欢迎指正"。无法核实的精度是负资产："1996 年"比"1996 年 9 月"诚实。

### 7. 给读者留门

自测题都有文中答案；在此之外留 **1 个开放真问题**——文中没有答案、作者自己也不知道的（"我一直没搞明白 X"）。一句话即可，这是给读者的邀请：评论区的高价值回答多半是这么问出来的。

## 常见错误

| 错误 | 症状 | 修正 |
|---|---|---|
| 手册腔 | 结构像官方文档，无钩子无台阶 | 回到骨架第 1、2 步重写开头 |
| 机制堆砌 | 讲完了"怎么做"但从没讲"为什么非这样不可" | 补第 3 步本质段落 |
| 被动阅读 | 全文代码都是"给读者看的" | 改成"让读者跑的"+ 预测输出 |
| 平铺直叙 | 所有段落同一深度，读者中途流失 | 显式分层，层间加台阶句 |
| 为了趣味硬凑 | 类比为类比而类比，与机制对不上 | 类比必须能映射到真实机制，映射不到就删 |
| 凭记忆转述旧文 | "上一篇说过……"与旧文原文对不上，或旧文根本没说过 | 打开旧文核对原文，链接用 permalink 格式 |
| 编造实验输出 | "预期输出"和真实运行的结果对不上 | 本地真跑摘录；跑不了就明说"示意输出" |
| 空洞的下一站 | 收尾只说"还有 X 值得探索" | 埋具体悬念（现象/反直觉断言），给下一篇明确的兑现点 |
| 假精确 | 凭记忆的日期精确到月份日、他人系统参数张口就来 | 核实，或降级为"印象中/约"；没把握就删精度 |
| 只报名字不算引用 | 提了 RFC/论文/文档却没有链接，或凭记忆"逐字"引用 | 关键出处给可点链接；没核对过原文就间接转述 |
| 全知姿态 | 通篇没有一处"我不知道"，自测题全有标准答案 | 留 1 个开放真问题，邀请读者补充 |
