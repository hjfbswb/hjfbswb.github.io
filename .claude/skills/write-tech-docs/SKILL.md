# 写深入浅出的技术文档

## 核心原则

读者要的不是"覆盖全部知识点的手册"，而是**一场被设计过的理解之旅**：先钩住，再分层爬升，中途亲手验证，最后看清本质。

基线（无 skill）的写作已经有钩子、有结构、有示例代码，不要在这些上面花重复功夫。**差距永远在这五件事：台阶、本质、动手、类比边界、事实纪律。**

下面的骨架是默认形状，不是六件套强制：短文（约 1500 字以内）可以砍掉收尾地图、把动手压成一个实验，但台阶和本质段是承重墙，砍掉文章就垮。

## 文章骨架（正面模板）

### 1. 钩子（开头 3 段以内必须出现其一）

- 一个读者真实踩过的坑 / 熟悉的困惑（"改了 CSS 用户却看不到新版"）
- 一个反直觉的事实或提问（"调用生成器函数时，函数体一行都没执行"）
- 一段可运行的 5 行代码，其输出违背读者预期

❌ 不要以"X 是一种……的技术"这类定义句开头。

### 2. 分层爬升（每层回答读者当下的一个问题）

| 层 | 读者状态 | 本层回答的问题 |
|---|---|---|
| L1 会用 | "先让我跑起来" | 最小可用做法是什么？ |
| L2 懂原理 | "它为什么这样工作？" | 底下发生了什么？ |
| L3 想得透 | "为什么非得这样设计？" | 换个设计行不行？代价是什么？ |

- 每层开头用一句话点明"你现在在哪一层"（如"到这里你已经会用了，但……"）。
- 相邻层之间必须有**台阶句**制造求知缺口："但这解释不了下面这个现象……"

### 3. 本质段落（全文的灵魂，L3 层的核心）

用一句话或一个心智模型回答："去掉所有术语后，这东西**到底是什么**？"

- 好的本质："生成器 = 把函数的执行状态变成可以拿在手里、随时暂停恢复的东西"
- 好的本质："HTTP 缓存 = 在'不问了省流量'和'问一句保新鲜'之间的信任分级"
- 检验标准：读者能用这句话向同事解释该技术，而不引用任何术语。

再追问一层设计权衡：**为什么是这个方案而不是显然的替代方案？**（列表 vs 生成器、绝对时间 vs 相对时间）说清被否决方案的失败场景，本质才立得住。

### 4. 趣味元素（散布全文，每千字至少一处）

- **生活化类比**：贴近读者真实经验的（外卖/快递/图书馆借阅），避免陈词滥调（造车、盖楼慎用）。每个类比交代一句**哪里失效**——类比是脚手架，拆掉后读者该留下机制本身。例："把 MEMORY 想成仓库平面图很管用，但平面图不会像 `AT> FLASH` 那样让一批货拥有两个地址。"映射不到真实机制要素的类比就是凑数，删。
- **历史/八卦**：这个设计当年是为了解决什么纠纷或事故？（PEP 背后的故事、某个 bug 的代价）
- **反直觉时刻**：主动指出"你以为 X，其实 Y"
- 幽默克制：一两处轻巧的比喻即可，不抖机灵、不用网络梗堆砌

### 5. 动手环节（实践性 = 读者亲手做，不是看代码）

- 至少一个**可复制运行的最小实验**（≤10 行），并给出**预期输出**
- 至少一处"先预测再看答案"：让读者猜输出/猜行为，再揭示
- 收尾留 1-2 个**自测问题**（能答出说明真懂了，答案指向文中某节）

❌ 只贴示例代码让读者"参考"不算实践。

### 6. 收尾地图（不是知识点复述）

- 一张速查表 / 决策表（什么场景用什么方案）
- 指向下一站：学会这个后，再看什么会"原来如此"

## 事实纪律（技术文章的信誉事故都在这里）

对底层细节的记忆是概率性的，而读者会照着文章做——一条错误的硬件断言或一个不自洽的数字，比一段平庸的文字伤害大得多。本站真实教训：初稿写"固件 200K、512K Flash 只剩 8K"，读者拿计算器一按就穿帮；"非对齐访问直接出错"在 Cortex-M4 上只对了一半（单条 LDR/STR 容忍，LDM/STM 才会挂）。三条纪律：

1. **数字自洽**：文中每个具体数字，读者算一遍要能对上；几处数字之间要能互相印证——用量、容量、百分比必须是同一笔账。写完把自己当成较真的读者，从头按一遍计算器。
2. **底层行为断言要查证**：涉及硬件 / CPU / 编译器 / 框架的具体行为（"非对齐访问会怎样""这个寄存器读了会不会清零""编译器一定会优化掉吗"），不凭"显然"写。拿不准就查手册、规范或权威资料；查不了就把断言改弱（"在 Cortex-M4 上""多数情况下""GCC -O2 下"），或删掉只写有把握的部分。
3. **代码和输出真实**：示例代码语法要在脑中过一遍编译——编译都过不了的示例比没有更伤信誉。声称"会输出 X"的实验，输出要确实成立，不为戏剧效果编造。

## 图示（文字讲不清位置和时序时，画图）

一图抵千言的三个场景：**空间/结构**（内存布局、数据结构、段与地址）、**时序**（启动流程、握手协议、中断响应）、**关系**（模块依赖、数据流向）。判断信号：同一段文字翻来覆去描述"谁在谁上面/左边/接下来"——这是在用文字画图，该真的画图了。

形式按内容选：

- **Mermaid**（流程图、时序图、状态图）：Chirpy 原生支持，front matter 加 `mermaid: true`，正文用 ```mermaid 代码块。
- **ASCII 图**（放在代码块里）：内存布局、地址表这类"位置即语义"的内容最合适——精确、随正文排版、以后好改。
- **图片**（复杂示意图）：放 `assets/img/posts/<文章名>/`，正文用绝对路径引用；矢量优先（SVG）。

图示纪律：

- 画图天然是验证器：布局图上每个偏移量、时序图里每一步都必须精确，画图的过程往往能揪出正文里含糊或写错的数字（真实案例：为伪共享文章画缓存行布局图时，复核偏移量发现 `pad[48]` 恰好让整个结构体仍挤在同一行，padding 完全不生效）。所以画图前后把涉及的数字当面算一遍。
- 每张图前后各一句导览：图不能自解释到不用讲——先说"看这张图时注意什么"，再从图引出下一步。孤零零夹在段落间的图等于没画。
- 图中标注与正文术语严格一致：正文叫"向量表"，图里就不能叫"中断表"，读者对不上号。
- 密度参考：每 1000–1500 字一张关键图，原理层（L2）最需要。
- 装饰性配图不要：不能加深理解的图（泛泛的机房照片、为"显得有图"而配的图）删。

## 系列文章衔接

本博客的文章常长在系列里（如 Cortex-M4 系列）。写系列新篇时：

- 动笔前扫一遍前篇：有没有埋过指向本篇的伏笔？有就在开头兑现（"上篇埋过一句伏笔……本篇兑现"）。
- 收尾给下一篇埋钩子："这里先记住，下篇展开。"
- 交叉链接用真实 URL 格式（`/2026/09/02/xxx.html`），写完后核对目标文章确实存在。
- 每篇仍要自足：没读过前篇的读者也能跟下来——用到前篇的机制时一笔带过补上，不要"见前篇"完事。

## 常见错误

| 错误 | 症状 | 修正 |
|---|---|---|
| 手册腔 | 结构像官方文档，无钩子无台阶 | 回到骨架第 1、2 步重写开头 |
| 机制堆砌 | 讲完了"怎么做"但从没讲"为什么非这样不可" | 补第 3 步本质段落 |
| 被动阅读 | 全文代码都是"给读者看的" | 改成"让读者跑的"+ 预测输出 |
| 平铺直叙 | 所有段落同一深度，读者中途流失 | 显式分层，层间加台阶句 |
| 编造底层行为 | "非对齐访问直接出错"，实际有例外 | 查证，或把断言改弱、写明适用条件 |
| 数字不自洽 | 用量、容量、百分比各说各话 | 以较真读者视角从头按一遍计算器 |
| 系列断篇 | 只有"见前篇"，没读过的读者卡住 | 一笔带过补机制，本篇自足 |
| 凑数类比 | 类比为类比而类比，与机制对不上 | 按映射检验 + 交代失效边界，否则删 |
| 文字画图 | 用三段文字描述一个内存布局 | 改成 ASCII/Mermaid 图 + 前后导览句 |
