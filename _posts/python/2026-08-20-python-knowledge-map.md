先做一个小测验。下面这段代码不到十行，涉及五个知识点。**先别运行**，逐行猜猜输出是什么：

```python
fs = [lambda: i for i in range(3)]
print([f() for f in fs])

def counter():
    n = 0
    def inc():
        nonlocal n
        n += 1
        return n
    return inc

c = counter()
print(c(), c(), c())

import sys
print(sys.getsizeof([None] * 1000), sys.getsizeof(range(1000)))
```

答案是 `[2, 2, 2]`、`1 2 3`、`8056 48`。如果你三组全猜对，这篇你大概率可以跳过；如果有任何一组让你愣住，恭喜，你正好撞见了这篇文章要讲的事。

很多 Python 学习者的困惑不是"某个知识点不懂"，而是"知识点太多、太散，不知道它们之间是什么关系"。装饰器、闭包、生成器、迭代器、协程、`yield from`、`itertools`……教程里每个都讲过，但它们在脑子里是一堆互不相识的名词，像一本没有目录的词典。

这篇不教你任何新知识，只做一件事：**把已写的这一系列文章放进一张地图里，标清谁站在谁肩膀上**。你会发现，那张"知识清单"其实是一座塔--底层极小，上层所有看起来很新的特性，都是底层几块积木的重新组合。

## L1：先拿到地图--五层塔，自底向上

你现在在第一层，目标只有一个：知道每个知识点大概住在几楼，学的时候别坐错电梯。

整座塔长这样（每层只依赖它下面的层，绝不跳层）：

```
第 5 层  工程            module / package / __slots__ / itertools
第 4 层  组合            装饰器 / yield from / 协程
第 3 层  积木            生成器 / 闭包 / 匿名函数与高阶函数
第 2 层  协议            迭代器协议 / 一切皆对象 / 作用域规则
第 1 层  地基            对象模型、名字与绑定、函数调用
```

逐层看一下，已经成文的地方附上链接（本系列的已写篇目都在这里了）：

**第 1 层：地基。** Python 里最值钱的一句话是"一切皆对象"--函数是对象，类是对象，模块还是对象。再加上"变量只是绑向对象的名字"和 LEGB 作用域规则，这一层薄薄三块砖，撑起了上面所有楼。[《Python 的函数》](/2019/12/22/python-function.html)是这层的旧文。

**第 2 层：协议。** `for` 循环为什么不挑食，列表、文件、字典、生成器通通能吃？因为它们背后是同一个**迭代器协议**：`__iter__` 加 `__next__`。想弄懂"为什么列表能 for 却不能 next"，看[《Python 迭代器》](/2026/08/17/python-iterator.html)。

**第 3 层：积木。** 三块可以拿在手里反复用的东西：

- [生成器](/2026/08/17/python-generator.html)--把函数的执行状态变成可暂停、可恢复的对象；
- [闭包](/2026/08/18/python-closure.html)--让函数记住自己出生时的环境；
- [匿名函数与高阶函数](/2026/08/18/python-lambda-hof.html)--把代码本身当成值传来传去。

**第 4 层：组合。** 这一层没有新机制，全是第 3 层积木的拼装：

- [装饰器](/2026/08/18/python-decorator.html) = 高阶函数 + 闭包，拼在"函数诞生"的那一刻；
- [yield from](/2026/08/18/python-yield-from.html) = 生成器 + 生成器，一个把暂停权委派给另一个；
- [协程](/2026/08/18/python-coroutine.html) = 生成器 + 事件循环，`yield` 的"暂停"被赋予了"我在等 IO"的语义。

**第 5 层：工程。** 积木搭好了，怎么在真实项目里用得体面：[module 与 package](/2026/08/18/python-module-package.html)管代码怎么组织、`import` 到底执行了什么；[`__slots__`](/2026/08/17/python-slots.html)管一百万个对象怎么塞进内存；[itertools](/2026/08/18/python-itertools.html)是迭代器协议预制好的一盒标准零件。

注意一件事：塔上没有"装饰器专用协议"、"协程专用语法糖"这种东西（`async/await` 的关键字除外，那是给解析器看的）。**每一个上层概念，拆开都是下层概念的组合。**这就是为什么它们能被"讲透"--不是因为文章写得好，是因为它们本来就没有藏着新机制。

## L2：塔是依赖图--为什么必须自底向上学

到这里你已经拿到地图了，但地图上还有一个问题没回答：为什么不能随便挑一篇开始读？

因为这张图的本质不是"分类图"（按主题把知识归堆），而是**依赖图**（按"理解 X 之前必须先理解 Y"连线）。分类图怎么走都行，依赖图走错顺序就处处碰壁。

用开头的测验当例子。三行输出各自连着一条依赖链：

- `[2, 2, 2]` 这条链是：**作用域规则 -> 闭包 -> lambda 捕获**。`lambda: i` 里的 `i` 不是"定义时拷贝了一个值"，而是"指向外层名字的引用"，三函数共享同一个 `i`，循环结束时它已经是 2。不先懂名字绑定，`[2, 2, 2]` 就永远是玄学；懂了名字绑定，[闭包那篇](/2026/08/18/python-closure.html)开头的同款谜题会当场解开。
- `1 2 3` 这条链是：**嵌套作用域 -> nonlocal -> 闭包持有的是 cell 而不是快照**。同样是闭包，为什么一个记住了"活的变量"，一个却"共享到出错"？两个现象共用一个机制。
- `8056 48` 这条链是：**迭代器协议 -> 惰性求值 -> range 不是列表**。`range(1000)` 为什么只有 48 字节？因为它压根没存那一千个数，它只是一个记得"从几到几、步长多少"的可迭代对象，被 `next` 的时候才现算。这条链一直通到生成器和 itertools。

把这个"往下挖"的方法反过来用，就是学习顺序：**遇到一个不懂的上层概念，别在原地反复读，顺着依赖图往下一层挖，挖到底再爬回来。**看不懂装饰器，八成是闭包没通；看不懂协程，八成是生成器的暂停语义没抓住。原地打转和下潜一层再浮上来，花的力气差不多，收获差一个量级。

还有一个自检信号值得记住：如果一个"新知识点"让你觉得"这也太多了吧"，通常说明你把它当成了第 1 层的地基砖，而它其实是第 4 层的组装件--拆开看看，里面全是老朋友。

## L3：这座塔为什么长这样--小内核，大组合

你现在在第三层，也是最透的一层。退后两步眯起眼看整座塔，问一个问题：**Python 为什么选择"极小的内核 + 反复组合"，而不是"每个特性一套专用机制"？**

先说本质。去掉所有术语，Python 的知识图谱只有一块地基砖：

> **万物皆对象，对象之间靠少数几个公开协议对话。**

迭代器协议是"怎么逐个要东西"的对话格式；`__call__` 是"怎么被当函数用"的格式；`__enter__`/`__exit__` 是"怎么配合 with 收拾现场"的格式。语言只负责定义格式，不关心谁来实现。`for` 不认识列表，列表也不认识 `for`，它们只是碰巧都会说"迭代器"这门普通话。

有了这块砖，上层每个"新特性"的成本都低得惊人：

- 装饰器（PEP 318）当年吵了好几年，吵的核心就是"要不要引入一个新机制"。最后的定案恰恰是**不引入**--`@decorator` 只是一行 `f = decorator(f)` 的语法糖，内核零改动。Guido 在 PEP 里明确说过：如果装饰器需要新机制才能工作，那这个提案就是错的。
- 协程的演化更极端：`asyncio` 不是"加了个并发系统"，而是发现生成器的暂停/恢复**本来就可以**表达"我在等 IO"，于是先有了 `yield from` 委派（PEP 380），再有了事件循环接管，最后才有了 `async/await` 关键字把"生成器"和"协程"在语法上分开。整条演化路径没有一步是推翻重来。

再追问一层：**专用机制这个"显然的替代方案"输在哪？**假设语言为装饰器专门做一套机制：解析到 `@` 就走特权通道。那么你自己写的普通函数就没法干同样的事了，工具库（比如各种注册框架）会被排除在外；每加一个特性，解释器、类型检查器、教程各胖一圈，而使用者要背的东西线性增长。组合式设计的代价是"初次理解需要拆包"（这正是本系列文章存在的原因），收益是**知识不随语言版本线性膨胀**--这十年来 Python 加了很多特性，但第 1、2 层几乎没动过。

顺带一提，`__slots__` 是塔里少数往回看的知识点：它不是新积木，而是给"一切皆对象"这块地基本身做的一次性能妥协--对象默认背着 `__dict__` 这个背包，一百万个实例时就该给它们换上紧身衣了。

## 动手环节：一段代码，把整座塔走一遍

光看地图不算数。下面这段不到 15 行的代码，从下到上穿过五个层。老规矩，**先预测输出，再运行**：

```python
import sys

def trace(func):                        # 第 3 层：闭包 + 高阶函数
    def wrapper(*args, **kw):           # 第 1 层：*args 是名字绑定
        print(f"调用 {func.__name__}")
        return func(*args, **kw)
    return wrapper

@trace                                  # 第 4 层：装饰器 = trace(evens)
def evens(n):                           # 第 3 层：生成器
    for i in range(n):                  # 第 2 层：迭代器协议
        if i % 2 == 0:
            yield i

print(list(evens(6)))                   # 你猜这里打印几行"调用"？
print(sys.getsizeof(evens(10_000_000))) # 你猜这个有多大？
```

两个预测点，想好了再看答案：

1. **`list(evens(6))` 打印几行 `调用 evens`？** 一行。装饰器在 `evens` **诞生时**就把它换成了 `wrapper`，之后无论调用多少次、产出多少个值，`@trace` 那行代码只执行一次。产出 3 个偶数是迭代器协议在干活，和装饰器无关--两层各司其职，互不知晓。
2. **`getsizeof(evens(10_000_000))` 多大？** 两百字节左右，和 `n` 的大小毫无关系。生成器对象里没有一千万个数，只有代码指针和一小段冻结的执行状态；每次 `next` 才执行到下一个 `yield`。把 `10_000_000` 改成 `10_000_000_000`，内存占用一个字节都不涨。

一段代码，五层楼全亮了灯。如果哪个预测错了，那张地图上就标出了你该去补的房间号。

### 自测问题

1. `@trace` 那行代码，是在 `evens` 被定义时执行，还是在 `evens(6)` 被调用时执行？为什么这能证明"装饰器没有新机制"？
2. 把 `evens` 里的 `yield i` 改成 `return [i for i in range(n) if i % 2 == 0]`，函数立刻从生成器退化成普通函数。`sys.getsizeof` 的结果会发生什么量级的变化？这背后是哪一层的知识点？
3. 协程那篇说 `async/await` 是"被事件循环标准化的生成器"。如果 Python 当年没有生成器，协程还能这样"顺手"长出来吗？说说你的推理。

**塔上还没盖的楼层**（本系列下一篇的候选，按依赖顺序排）：

- **上下文管理器**（`with`）：第 2 层的又一门协议，和迭代器是同班同学；
- **描述符与属性查找**（`property`、`classmethod` 的真身）：装饰器语法糖底下真正的机制，通往元类的必经之路；
- **元类与 `__init_subclass__`**：ORM 框架们魔法的源头，塔尖往下的最后一层；
- **GIL 与并发模型**：协程篇留下的那条岔路--什么时候必须多进程；
- **类型注解与 `typing`**：又一代"协议"故事的最新章节。

下一站建议别按顺序读，而是做个实验：随手挑一个你平时"会用但说不清"的特性，试着把它拆到第 2 层为止，看看拆出来的零件是不是全是这张地图上的老面孔。**当你发现每个新名词都能拆成三个旧名词时，这张地图就算装进脑子里了--而 Python 以后再出新特性，对你来说也只是又一笔组合，而不是又一篇要背的课文。**
